## 一、產品定位

### 一句話定位

OddSpot 是一張台灣奇景地圖：收錄怪廟、巨物、都市傳說、荒謬地景這類「B 級景點」，
讓使用者用地圖或滑卡片找到下一個想去的怪地方，排成今日行程後直接導航出發。

視覺語言：Acid/Y2K，「一點點壞掉的 B-grade 存檔系統」。這不是裝飾，是產品識別的一部分。

### 誠實的雙重定位

本專案同時有兩個身分，衝突時以第一個為準：

1. **2026 求職季的 Hero Piece（主）**：目標讀者是面試官與技術主管。
   價值在於「一個人把 Mapbox、NextAuth、Prisma、Blob、Guest sync、審核流程串成
   完整可上線的產品」，以及有辨識度的視覺系統。
2. **真實可用的產品（副）**：真的有人會用它找景點。使用者成長是加分，不是目標。

推論出的決策原則：

- 「能不能在 5 分鐘 demo 裡展示」比「功能多不多」重要。
- **沒上線的功能對定位一的價值趨近於零**。上線 > 新功能，永遠成立。
- 視覺 polish 只在核心流程無死路之後才有價值。

## 二、目標使用者

### 主要：面試官 / 技術主管

- 停留 2–5 分鐘，多半用桌機打開連結，部分會用手機掃一眼。
- 想看的東西：完整流程、工程判斷（安全邊界、狀態同步）、視覺辨識度。
- 對應需求：首頁 30 秒內能理解產品在幹嘛；不能有死路或報錯；README / case study 要能講故事。

### 次要：奇景探索者

- 20–35 歲，喜歡怪地方、廢墟、B 級景點的人；以手機使用為主。
- 核心旅程：打開地圖 → 看到附近的怪東西 → 滑卡片或點 marker → 收藏 →
  排今日行程 → 跳外部導航出發 → （v2）回報到訪。
- 對應需求：手機手勢穩定、外部導航 fallback 可靠、投稿後知道自己的東西去哪了。

## 三、核心功能範圍（MVP v1）

以下六塊構成完整產品迴圈，v1 只做這些：

| # | 功能 | 狀態 | 一句話範圍 |
|---|------|------|-----------|
| 1 | 地圖探索 | ✅ 完成 | Mapbox + 4 主題、附近景點、filter/radius、marker/popup |
| 2 | 滑卡片探索 | ✅ 完成（待真機 QA） | 整合在 `/map` 探索模式：左滑略過、中間 + 收藏、右滑收藏並加入行程 |
| 3 | 今日行程與路線 | ✅ 完成 | 最多 5 點、拖曳排序、最佳化重排、路線顯示、外部導航（含 iOS fallback） |
| 4 | 收藏與同步 | ✅ 完成 | Guest localStorage 收藏 → 登入後同步到 DB；`/saved` 個人收藏頁 |
| 5 | 投稿與審核 | ✅ 完成（缺 reject reason） | 登入投稿 → pending → admin 審核 → active/rejected；防濫用；`/submissions` 狀態頁 |
| 6 | 認證 | ✅ 完成（待 production 驗證） | NextAuth v5 + Google/LINE OAuth |

v1 的 Definition of Done（達成才算「完成 MVP」，也才允許資源流向其他專案）：

1. Production 部署完成：Vercel env、OAuth callback、Blob、DB migration 全部實測通過。
2. 四種真機環境跑過核心流程：iPhone Safari、Android Chrome、iPadOS Safari、桌機 Chrome。
3. 投稿 → 審核 → 上架 → 被別人看到，整條迴圈在 production 走通。
4. 有一個可以公開分享的 URL 和一份能講 5 分鐘的 demo 腳本。

## 四、明確不做什麼（v1 凍結清單）

以下項目在 v1 DoD 達成前**不投入任何時間**，理由統一是：拉高維護成本但不改變
面試官看到的東西。

| 不做 | 說明 |
|------|------|
| 社群功能 | 動態牆、留言、追蹤、按讚，全部不做 |
| 複雜收藏夾 | 不做分類、資料夾、標籤；一個 saved 清單就夠 |
| AI 審核 / AI 內容生成 | 人工審核量在 v1 規模下完全可行 |
| 到訪驗證、足跡地圖、熱力圖 | v2 再議（`MVP-v2.md` 有草稿） |
| 評分 UI | `rating`、`visitCount` 欄位保留但 UI 不顯示 |
| 原生 App / PWA 離線 | 不做 |
| **Landing 3D 新迭代** | globe/moon/eye morph 相關 spec（2026-04-27、04-28、05-02）全部凍結在現狀。已實作的效果保留，未實作的不再開工。理由見下方專節 |
| 檢舉回報、週期性 Blob cleanup | v1.1 再做，admin reject 已會清圖 |
| 完整多語系 | next-intl 維持現有用法，不擴充語言 |

### 關於 Landing 3D 的誠實判斷

4–5 月大量投入的 3D 實驗（月球點雲、潮汐殼、眼睛 morph、石膏頭像）技術含量高，
且已在 Vault 沉澱成 7 份技術筆記——**這部分的求職價值已經被收割了**。
繼續迭代 landing 3D 的邊際報酬遠低於「把產品部署上線」。
未 render 的實驗元件應從 bundle 中隔離或移除（見技術規格書）。

## 五、與 parti 的資源取捨

### 現況事實

截至 2026-07-03，整個 Vault（含 40_Projects、99_Archive）**找不到任何 parti 的紀錄**。
這代表 parti 目前只存在於腦中或其他地方，沒有明確的範圍、目標、進度定義。

### 取捨規則（衝突時依序適用）

1. **OddSpot v1 DoD 未達成前，parti 的時間配額是 0。**
   依據：求職策略筆記明確把 Month 1–3 定為「OddSpot 收尾上線」，
   OddSpot 是目前唯一的 Hero Piece，一個 90% 完成但沒上線的作品在履歷上等於不存在。
2. **parti 要啟動的前置條件**：先在 `~/Vault/40_Projects/parti/README.md` 寫下
   一頁定義（目標、範圍、和 OddSpot 的差異化、預估時數）。寫不出這一頁，
   就還不到啟動的時候。
3. **啟動後的定位**：parti 對應求職策略的「Month 4–6 第二個小作品」槽位——
   它應該是**小而完整**的作品（2–4 週可上線），不是第二個 OddSpot 規模的專案。
4. **每週檢查點**：如果某週在 parti 上花的時間 > OddSpot，而 OddSpot DoD 還沒達成，
   視為走偏，下週修正。

## 附錄：資訊架構收斂原則

roadmap 已指出「入口太多、使用者不知道下一步」是最大 UX 缺口。收斂原則：

1. `/map` 是唯一主入口，其他頁面（`/saved`、`/submissions`、`/spots/[id]`、`/submit`）
   都必須有回到 `/map` 的明確路徑。
2. 每個「寫入動作」（收藏、加入行程、投稿）完成後必須給出「去哪裡看結果」的入口。
3. 滑卡三個動作（略過 / 只收藏 / 收藏＋行程）需要一次性的 onboarding 提示，
   不靠使用者自己猜。
